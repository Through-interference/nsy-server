# Телеметрия 300 кбит/с и приёмка на 3 км

Рабочий вариант для критериев Ильфара Губайдуллина — отдельный WFB/Wi-Fi-канал
телеметрии на Raspberry Pi и НСУ. Камера и GStreamer в этом режиме не запускаются.
Существующий ESP32/SX1262 CAN-мост остаётся отдельным каналом: его UART 115200
и GFSK250 не обеспечат 300000 бит/с полезных данных. Максимум SX1262 в FSK —
300 кбит/с физического потока, до заголовков и подтверждений
([Semtech](https://www.semtech.com/products/wireless-rf/lora-connect/sx1262)).

Для обычного 90-секундного замера живого UDP-потока на каждой стороне есть
`sudo bash measure-telemetry.sh --interface wlan1 ...`. Остальные параметры
совпадают с `start-telemetry.sh`; для тестового потока на Pi явно добавить
`--benchmark-seconds 60`. Параметры, указанные после скрипта, позволяют изменить
длительность. `--plan` выводит команды без настройки радио.

## Критерии и границы проверки

| Критерий | Как подтверждаем |
|---|---|
| Дальность не менее 3000 м при прямой радиовидимости | Реальные разнесённые точки, GPS/GPX обоих концов, фото/схема трассы и подписанный полевой протокол |
| Не менее 300000 бит/с полезной телеметрии | На НСУ: уникальные проверенные байты UDP-приложения ×8 / полное время измерения, включая паузы |
| Смена частоты при потере связи | На обоих концах: `link_down` → `channel_verified`/`channel_changed` → `link_restored` на одной резервной частоте, свежие двусторонние ACK |
| Учёт мощности | Запрошенный лимит и readback драйвера, усиление/поляризация/высоты антенн, потери фидера и согласованное для места испытаний ограничение ЭИИМ |

Минимальная серия по умолчанию — 60 секунд. Генератор предлагает 330000 бит/с,
чтобы при небольших потерях приёмник мог получить не менее 300000 бит/с.
Порог потерь 1% выводится как дополнительный настраиваемый показатель; он
не подменяет отдельный критерий полезной скорости. Продолжительность и
допустимые потери нужно согласовать с принимающей стороной.

Нагрузочный поток помечается `generated_load`: он проверяет пропускную способность,
а не наличие или смысл показаний настоящего автопилота. Для реальных данных есть
UDP-вход/выход; их тип помечается `live_udp`. Заголовки TLM1, UDP/IP, WFB, FEC,
heartbeat и дубликаты в полезную скорость не входят.

## Соответствие исходному проекту

Источник: предоставленная командой презентация «Финальная аттестация», слайды
5 и 10–14. В ней указаны испытания LoRa до ~1,5 км, задержки >500 мс,
неподтверждённая дальняя работа GFSK и недостигнутые 300 кбит/с. Новая схема
использует согласованный UDP-источник бортового компьютера и WFB вместо попытки
получить эти показатели повышением скорости LoRa.

Критерии Ильфара из сообщения команды задают приоритет ближайшей демонстрации.
Остальные пункты исходного ТЗ этим не отменяются:

| Пункт исходного ТЗ | Статус этой реализации / необходимая проверка |
|---|---|
| ≥300 кбит/с команд и телеметрии | Есть двусторонний UDP-канал; нагрузочная серия измеряет телеметрию Pi → НСУ. Скорость и выполнение команд в обратном направлении отдельно не аттестованы |
| ≥3 км при прямой видимости | Нужен полевой тест новой WFB-схемы; результат прежнего LoRa на 1,5 км не переносится на неё |
| Минимум две антенны на борту | Записать модель, число/монтаж/поляризацию и приложить фото; программно не подтверждено |
| Стабильная сеть 2–3 БВС | Текущий запуск — одна пара. Совместная работа и доступ нескольких БВС не проверены; смена частоты одной пары не реализует TDMA/мультидрон |
| Задержка <50 мс | Не измерена. Журналы разных компьютеров без подтверждённой синхронизации не являются измерением односторонней задержки |
| SNR ≥3 дБ | Согласовать методику и исследовать настоящие RX_ANT/PKT-журналы WFB. Локальная UDP-проверка не измеряет SNR |
| −20…+30 °C, природные помехи/ЛЭП | Не проверено программными тестами |
| Видео ≥10 Мбит/с либо согласованная альтернатива с распознаванием | В этой серии камера выключена; этот пункт не закрывается нагрузочной телеметрией |

## Перед выездом

1. Использовать исправления восстановления из предыдущих PR и одинаковую
   версию TLM1 на двух концах. Проекты не импортируют исходники друг друга.
2. Подготовить Linux, совместимый выделенный monitor/injection-адаптер и
   закреплённые WFB-бинарники по существующей инструкции проекта. Пара ключей
   одна: `drone.key` на Pi и соответствующий `gs.key` на НСУ.
3. Остановить остальные WFB/видеорежимы выбранного радио. Доступ к Pi оставить
   по отдельному Ethernet. Программа проверяет отсутствие глобального IP на
   выделенном интерфейсе, свободные локальные порты и блокировку своего режима.
4. Выбрать доступные на **обоих** адаптерах и разрешённые в месте испытания
   основную/резервную частоты и мощность. 2412/2462 МГц в командах — пример
   совместимого плана HT20, а не подтверждение его допустимости в любой стране.
5. Заполнить `config/site.example.json` реальными координатами, данными антенны и
   согласованным пределом ЭИИМ; сохранить как `site-air.json` / `site-ground.json`.
   В шаблоне `null` специально не принимается как измерение.

Мощность автоматически не повышается, regdomain не меняется. Если задан
`--tx-power-dbm`, применяется `iw ... set txpower limit`, и программа проверяет
readback после каждого переключения. Неизвестный readback или превышение лимита
останавливает тест. Показание драйвера не является измерением мощности RF-метром.

Для планирования: свободнопространственные потери на 3 км при 2412 МГц составляют
около 109,6 дБ по [ITU-R P.525](https://www.itu.int/rec/r-rec-p.525). Формула бюджета:
`P_rx = P_tx + G_tx + G_rx − L_tx − L_rx − FSPL − прочие потери`.
Использовать измеренный запас относительно чувствительности именно вашего
адаптера/MCS0. Радиус первой зоны Френеля в середине этой трассы около 9,7 м;
низкие антенны над ровной землёй могут существенно перекрывать её. Проверить
профиль трассы, высоты, прямую видимость и совпадение поляризации. Этот расчёт
не подтверждает дальность и не требует повышать мощность.

## Планы запуска без изменения радио

В bvs-camera:

```bash
bash start-telemetry.sh --interface wlan1 --plan
```

В nsy-server:

```bash
bash start-telemetry.sh --interface wlan1 --plan
```

WFB stream 2 переносит телеметрию и heartbeat Pi → НСУ; stream 3 — обратные
heartbeat/ACK и UDP-команды. Используются MCS0/HT20/long GI, FEC4:8 на борту и FEC1:3 на земле.
Физическая нагрузка выше полезных 300 кбит/с; факт выбора MCS или FEC сам по себе
не является измерением скорости. Обратные UDP-команды поступают в потребителя Pi;
смысл и выполнение команды подтверждает протокол бортового приложения.

## Серия A: пропускная способность на реальной дистанции

На каждом компьютере задать переменную `TX_POWER_DBM` согласованным лимитом
именно его передатчика; пример не назначает универсальный численный предел.
Указать реальное имя выделенного адаптера. Каталоги результатов должны быть новыми.

На НСУ из nsy-server:

```bash
sudo bash start-telemetry.sh --interface wlan1 --frequencies 2412 2462 \
  --tx-power-dbm "$TX_POWER_DBM" --site-json site-ground.json \
  --seconds 90 --output results/acceptance-capacity-ground
```

На Pi из bvs-camera:

```bash
sudo bash start-telemetry.sh --interface wlan1 --frequencies 2412 2462 \
  --tx-power-dbm "$TX_POWER_DBM" --site-json site-air.json \
  --benchmark-seconds 60 --offer-bps 330000 --target-bps 300000 \
  --seconds 90 --output results/acceptance-capacity-air
```

Генератор запускается после подтверждения обоих направлений. Последовательность,
контрольная сумма и известный шаблон проверяются на НСУ. Конец серии содержит
счётчики передатчика и повторяется несколько раз. Потеря этого сообщения
не превращает неполную нагрузочную серию в успешную. Время, потраченное на
первичное установление связи, отдельно видно в журнале; паузы **внутри** измерения
из знаменателя скорости не исключаются.

## Серия B: контролируемая потеря и смена частоты

Запустить новую пару серий. На НСУ добавить к параметрам радио:

```bash
--outage-after 10 --outage-seconds 5 --seconds 65 \
--output results/acceptance-recovery-ground
```

На Pi использовать новую директорию и нагрузку:

```bash
--benchmark-seconds 40 --seconds 65 \
--output results/acceptance-recovery-air
```

Через 10 с после установления связи НСУ приостанавливает **свой дочерний**
обратный `wfb_tx` на 5 с и пишет `outage_injected` с причиной `pause_owned_wfb_tx`.
После потери свежего подтверждения оба конца ищут партнёра: время пребывания
на частоте 1,5 с для Pi и 4,5 с для НСУ, таймаут связи 3 с. После встречи на
доступной частоте heartbeat подтверждают оба направления и поиск прекращается.
Восстановление частоты считается зафиксированным, только если оба журнала
показывают readback и восстановление на одной резервной частоте.

Это контролируемый обрыв обратного передатчика, а не тест устойчивости против
помех и не измерение чувствительности. Потери этой серии ожидаемы и остаются
в отчёте. Для приёмки показать механизм обрыва и запись обоих экранов/журналов.
Отдельно проверить отсутствие ложных переключений при стабильной связи.

## Реальная телеметрия

Согласованный источник — UDP с бортового компьютера. Запустить тот же radio-режим **без** `--benchmark-seconds`. На Pi приложение
принимает UDP на `127.0.0.1:14550` (`--input-port`). На НСУ исходные UDP-пакеты
отправляются на `127.0.0.1:14550` (`--output-port`). Обратные UDP-команды принимаются
на НСУ на `127.0.0.1:14551` (`--input-port`) и выдаются приложению Pi на
`127.0.0.1:14551` (`--output-port`). Максимум 1100 байт на пакет;
более крупные пакеты отклоняются и учитываются. Нагрузочный шаблон B никогда
не передаётся приложению-потребителю.

Если бортовой компьютер — отдельное устройство Ethernet, на Pi явно указать
`--input-bind PI_ETHERNET_IP --input-peer ONBOARD_COMPUTER_IP`. Источник отправляет
UDP на этот адрес Pi и `--input-port`. Внешняя привязка требует заданного peer;
пакеты других IP отклоняются и отмечаются в журнале. Это фильтр локального
источника по IP, не дополнительная криптографическая аутентификация. Через эфир
пакеты по-прежнему защищает WFB.

Источник должен выдавать не менее 37500 полезных байт/с. Переход на WFB не
снимает ограничений входного интерфейса: UART 115200 не подходит, а Classical
CAN 500 кбит/с также нельзя считать 500 кбит/с полезной телеметрии. До приёмки
проверить реальный источник, протокол и потребителя; интеграция с автопилотом
не доказывается нагрузочным шаблоном. Для UART нужен достаточный запас скорости
после start/stop-битов; для CAN нужно учитывать ID/DLC, арбитраж, CRC и bit stuffing.

## Сводный протокол

Перенести каталоги обоих концов на один компьютер, сохранив файлы. Из nsy-server:

```bash
bash summarize-telemetry.sh \
  --air results/acceptance-capacity-air \
  --ground results/acceptance-capacity-ground \
  --recovery-air results/acceptance-recovery-air \
  --recovery-ground results/acceptance-recovery-ground \
  --output results/acceptance-protocol.md
```

Получаются Markdown и JSON. Проверяются SHA-256 исходных артефактов,
соответствие сессий/настроек, уникальные данные приёмника и записи передатчика.
Сохраняются `manifest.json`, `events.jsonl`, `status.json`, `report.json`, stdout
обоих WFB-процессов и хеши бинарников. Ключи и содержимое живой телеметрии
в журнал не записываются; записываются номера, длины и SHA-256 полезных данных.
В `events.jsonl` раз в секунду добавляется `sample` со скоростью, счётчиками,
состоянием связи и частотой; события переключений сохраняются отдельно в том же
файле. `status.json` содержит последний снимок. В manifest записываются commit,
признак локальных изменений и хеши Python-файлов под испытанием. При копировании
установленной версии без Git сохраняются хеши файлов.

Для дальности приложить GPS/GPX и время, фото/видео, профиль трассы, высоты
антенн и подписанный протокол. Введённые координаты дают расчёт расстояния,
но не независимое подтверждение фактического радиотеста. Поэтому генератор
отчёта не выставляет `all_requirements_confirmed=true` автоматически.

## Программная проверка без радио

Из nsy-server (оба checkout должны содержать TLM1):

```bash
python3 tests/check_telemetry_localhost.py --air-repo ../bvs-camera \
  --seconds 60 --output /tmp/telemetry-capacity-check
python3 tests/check_telemetry_localhost.py --air-repo ../bvs-camera \
  --seconds 20 --recovery --output /tmp/telemetry-recovery-check
```

`udp-test` не запускает WFB, не настраивает адаптер и не шифрует поток.
Его результат всегда имеет область `localhost_only_no_radio`; он не может
подтвердить эфирную скорость, переключение аппаратной частоты или 3 км.
